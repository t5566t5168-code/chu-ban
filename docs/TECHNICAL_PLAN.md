# TXT 閱讀器 MVP 技術方案

日期：2026-10-18

狀態：開發前方案，尚未實作

產品依據：[產品設計](../PRODUCT_DESIGN.md)

## 1. 方案結論

採用 **Electron + TypeScript + Vite + 原生 HTML/CSS**，製作本機桌面 TXT 閱讀器。以開發簡單、閱讀體驗穩定、方便後續迭代為優先，接受 Electron 自帶執行環境造成的安裝體積與基礎記憶體開銷。

第一版暫定先交付 Windows x64 版本；程式結構保留跨平台能力，macOS 與 Linux 待有實際需求後另行打包、測試。這是本方案的預設交付範圍，並非產品文件已確定的平台需求。

目前不引入 React、UI 元件庫、全域狀態管理、資料庫或遠端服務。閱讀內容只在記憶體中使用，不上傳、不保存檔案副本或閱讀位置。

## 2. 技術選型

| 項目 | 選擇 | 用途與理由 |
| --- | --- | --- |
| 桌面容器 | Electron | 建立視窗、提供原生選檔與本機檔案讀取能力。 |
| 開發語言 | TypeScript，啟用 strict | 約束檔案結果、畫面狀態及跨程序介面，減少狀態處理錯誤。 |
| 前端建置 | Vite | 提供開發伺服器與正式靜態資源建置。 |
| 閱讀介面 | HTML/CSS + TypeScript DOM 操作 | 畫面少、互動單純，無需額外前端框架。 |
| 桌面打包 | Electron Forge | 統一桌面開發、封裝與產物製作流程，建置階段接入 Vite。 |
| 套件管理 | npm + package-lock.json | 固定依賴解析結果，使用 npm ci 重現環境。 |
| 邏輯測試 | Vitest | 驗證 UTF-8 解碼、錯誤分類及檔案替換狀態等關鍵行為。 |

開發啟動時選定互相相容的 Electron、Forge、Vite 與 Node.js 版本，記錄於專案設定並提交 lockfile。Node.js 是開發工具需求；使用者執行打包後的應用不需要自行安裝 Node.js。

## 3. 模組分工

採用 Electron 的主程序、preload 與渲染程序分工：

```text
閱讀介面（renderer）
  → window.reader.openTextFile()
preload：提供有限、具型別的橋接介面
  → IPC
主程序（main）：選檔、驗證、讀取、解碼
  → 回傳取消／成功／失敗結果
閱讀介面：更新內容或顯示提示
```

- **主程序**：管理視窗與應用生命週期、開啟原生檔案選擇器，以非同步檔案 API 讀取資料，處理 UTF-8 解碼與錯誤分類。
- **preload**：只公開 `openTextFile()` 這類特定功能，不公開任意路徑讀取、完整 IPC 或 Node.js API。
- **渲染程序**：管理首頁、閱讀頁、讀取中狀態及提示；處理文字排版、鍵盤操作與捲動。
- **共用型別**：定義選檔結果及錯誤碼，讓主程序與介面遵循同一份契約。

建議目錄如下；此處描述未來實作結構，不代表目前已有這些程式：

```text
docs/                  技術文件
src/
  main/                視窗、IPC、檔案讀取
  preload/             安全橋接介面
  renderer/            HTML、CSS、閱讀互動
  shared/              共用型別與錯誤碼
tests/                 關鍵邏輯測試與小型測試資料
demo/                  現有瀏覽器原型
```

現有 `demo/` 作為視覺與操作參考，將適用的排版與互動遷移至正式程式。原型中的示範文章、模擬錯誤入口不納入正式功能；正式版使用系統字體或隨應用提供的資源，移除外部 Google Fonts 依賴，以確保離線使用。

## 4. 檔案開啟與狀態規則

1. 使用者點擊開啟或更換檔案後，進入讀取流程；期間停用重複選檔入口，避免多個請求互相覆蓋。
2. 主程序提供單檔 `.txt` 選擇器，選定後再次檢查副檔名，不區分大小寫，並確認可作為一般檔案讀取。
3. 以非同步方式讀取位元組，使用嚴格 UTF-8 解碼（`TextDecoder` 的 `fatal: true`），允許 UTF-8 BOM。無效位元組序列回傳「僅支援 UTF-8」提示，不靜默替換成亂碼。這是驗證 UTF-8 是否有效，不是自動辨識或轉換 Big5、GBK。
4. 成功後回傳檔名與文字；渲染程序一次完成內容替換，再將閱讀區捲回頂端。
5. 取消選檔或開啟失敗時，保留原有檔名、內容與捲動位置；若尚未開啟檔案，則保留首頁。
6. 成功開啟空白檔案時，更新檔名並顯示「此檔案沒有可閱讀的內容」。空白包含零位元組、只有 BOM，或只有空白與換行的內容；判斷時不修改正常檔案的原文。
7. 無論成功、取消或失敗，結束後都恢復選檔入口。錯誤提示區不取代目前的閱讀內容。

跨程序結果採用明確的三種分支：`cancelled`、`success`、`error`。成功結果包含 `fileName`、`text`；失敗結果包含可識別的錯誤碼，例如副檔名不符、UTF-8 無效、讀取失敗。介面依錯誤碼顯示簡短中文，不直接呈現系統例外或完整檔案路徑。

## 5. 閱讀排版與效能

- 使用純文字節點或 `textContent` 顯示檔案，不將內容當作 HTML 解析。
- 使用 `white-space: pre-wrap` 保留換行與空白，配合 `overflow-wrap: anywhere` 避免長行溢出。
- 閱讀區設定最大寬度、左右留白與舒適行距，採單一垂直捲動區域；保留固定可見的更換檔案入口。
- 提供語意化按鈕、可見焦點及狀態提示，支援鍵盤選檔與閱讀操作。
- 第一版先採整檔讀取與簡單文字渲染，不逐字建立 DOM，也不預先導入虛擬捲動或分頁引擎。

非同步讀檔不代表解碼與渲染完全不會阻塞。實作後必須使用完整長篇小說及較大 TXT 試讀，記錄檔案大小、字數、測試機規格、開啟耗時及捲動表現。若觀察到明顯停頓，再依瓶頸採用背景解碼或分段渲染；不假設更換桌面框架即可解決問題。

產品目前沒有最大檔案大小的定義，本方案不自行加入硬性限制，也不承諾任意大小檔案都能流暢開啟。驗收時記錄已驗證範圍，若需要限制則另行確認產品行為。

## 6. 安全與離線運作

- 視窗明確設定 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。
- 主程序只接受預定的 IPC 功能，驗證呼叫來源；檔案路徑來自原生選檔結果，不接受介面任意傳入路徑。
- 正式版僅載入打包的本機介面資源，設定限制性的 Content Security Policy，阻擋非預期導覽及新視窗。
- preload 以適合 sandbox 的單一腳本產物建置，避免依賴 sandbox 中不可用的 Node.js 模組。
- 不需要帳號、網路請求或背景服務；正式版不啟動原型使用的本機 HTTP 預覽伺服器。

## 7. 開發與交付步驟

1. **專案骨架**：建立 Electron、TypeScript、Vite 與 Forge 設定，確認開發視窗與正式封裝都能啟動。
2. **核心流程**：完成主程序選檔、UTF-8 解碼、IPC 契約，以及成功、取消、失敗的狀態處理。
3. **閱讀介面**：參考現有原型完成首頁、閱讀區、檔名與提示，加入換檔捲回頂端行為。
4. **驗證與交付**：完成邏輯測試、實際小說試讀、離線檢查與 Windows 打包測試。

預計提供開發啟動、型別檢查、測試、封裝及製作發佈產物的 npm 指令。第一版先交付 Windows x64 可執行壓縮包供本機試用；公開發佈時再處理安裝器、程式簽章與發佈渠道。未簽章版本可能出現 Windows 信任提示，應在試用說明中註明。自動更新不在第一版範圍內。

每次完成改動後依 `AGENTS.md` 建立對應 Git commit，方便追蹤與回滾。

## 8. 驗收方式

| 驗證面向 | 檢查內容 |
| --- | --- |
| 解碼與文字 | 中英文、標點、Emoji、UTF-8 BOM、LF／CRLF、無效 UTF-8。 |
| 異常提示 | 空檔、純空白檔、副檔名不符、檔案不可讀或選取後消失。 |
| 狀態一致性 | 換檔成功才替換內容並回頂端；取消及失敗保留原內容與位置；讀取結束恢復操作。 |
| 排版 | 長行、無空格長字串、縮放與調整視窗時不產生文字溢出。 |
| 長文效能 | 以完整長篇小說測試開啟、捲動及連續換檔，記錄實測範圍與問題。 |
| 正式產物 | 在未安裝開發工具的 Windows 環境啟動，離線開檔，關閉重開後回到初始狀態。 |

自動化測試聚焦解碼與狀態轉移；原生選檔、視窗行為、閱讀舒適度及打包後操作以實際桌面驗收確認。

## 9. 後續擴充

閱讀進度、字體大小及深色模式可在後續加入本機設定儲存；書架與筆記出現實際資料管理需求時，再評估 SQLite。其他編碼以獨立解碼模組擴充。這些方向不提前加入第一版，也不要求現在改用 React 或引入資料庫。
